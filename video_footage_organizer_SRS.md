# Software Requirements Specification (SRS)
## Video Footage Organizer for macOS

**Document version:** 1.0  
**Status:** Initial formal specification  
**Target platform:** macOS, Apple Silicon  
**Primary core language:** C++  
**Proposed UI:** Swift/SwiftUI or AppKit over a C++ core  
**Persistence:** SQLite  
**Application type:** Local desktop application

---

## 1. Introduction

### 1.1 Purpose

This Software Requirements Specification defines the functional and non-functional requirements for a macOS application that organizes large collections of raw video footage using file/camera metadata and user-supplied organizational information.

The application is an organizer rather than a video editor. It provides a virtual, non-destructive organization workflow in which automatic organization is proposed, manually refined, reviewed, and finally applied to the physical filesystem.

### 1.2 Product Objective

The system shall allow a user to transform a collection of raw video files from an initially unstructured or partially structured state into a meaningful hierarchical organization while maintaining explicit control over physical filesystem modifications.

The core workflow is:

```text
Import
  ↓
Scan / Extract Metadata
  ↓
Select Organization Criteria
  ↓
Generate Virtual Proposal
  ↓
Human Review / Editing
  ↓
Review Filesystem Changes
  ↓
Apply
```

### 1.3 Scope

The MVP shall support:

- project creation and opening;
- recursive video import;
- metadata extraction;
- metadata normalization;
- virtual folders;
- clips;
- user-defined tags;
- automatic metadata-based organization;
- naming templates;
- manual organization overrides;
- tree editing;
- a visual hierarchy/canvas;
- undo;
- change review;
- safe filesystem application;
- missing-file detection.

The MVP shall not include video editing, AI video analysis, semantic video search, physical file deletion, duplicate merging, or file relinking.

# 2. Definitions

| Term | Definition |
|---|---|
| Project | The application's representation of one physical footage root and its organizational data. |
| Project Root | The physical directory containing the project's footage and `.project` file. |
| Clip | A database object representing one physical video file. |
| Folder | A virtual/project directory containing clips and/or child folders. |
| Metadata | Information extracted from a video file or camera. |
| Raw Metadata | Original metadata keys and values extracted from a file. |
| Normalized Metadata | Metadata mapped into application-standard categories. |
| Tag | User-created organizational vocabulary item assignable to clips. |
| Title | The clip's logical display/name value, eventually used for its physical filename. |
| Organization Proposal | A virtual hierarchy and naming arrangement generated by the organization engine. |
| Manual Override | A user decision that takes precedence over automatic organization for a clip. |
| Change | An explicit logical or filesystem operation such as moving or renaming a file. |
| Apply | The operation that converts approved virtual changes into physical filesystem changes. |
| Missing Clip | A clip whose expected physical file cannot currently be found. |

# 4. User Classes

## 4.1 Primary User

A video creator/editor/filmmaker who has substantial raw footage and wants to organize it before using a conventional editor.

The user is assumed to understand their footage semantically but does not necessarily understand camera-specific metadata formats.

## 4.2 System Administrator

Not applicable to MVP. The application is intended primarily for individual local desktop use.

---

# 5. Functional Requirements

## 5.1 Project Management

### FR-PROJ-001 — Create Project

The system shall allow the user to create a project associated with a physical footage root.

### FR-PROJ-002 — Project File

The system shall create a `.project` file within the project root.

### FR-PROJ-003 — Preserve Root Directory

The system shall not rename the project root directory.

### FR-PROJ-004 — Open Project

The system shall allow an existing `.project` file to be opened.

### FR-PROJ-005 — Single Active Project

The MVP shall maintain one active project at a time.

### FR-PROJ-006 — Project Persistence

The system shall persist project structure, clips, metadata, tags, organization configuration, and relevant state.

### FR-PROJ-007 — Schema Versioning

The project database shall contain a schema version to permit future migrations.

---

# 6. File Import Requirements

### FR-IMP-001 — Recursive Scan

The system shall recursively scan selected project/import directories.

### FR-IMP-002 — Supported Video Detection

The system shall identify supported video files and exclude unsupported files.

### FR-IMP-003 — Clip Creation

Each imported physical video shall result in a distinct Clip record.

### FR-IMP-004 — Existing Folder Structure

Existing physical subdirectories may be represented as the initial virtual folder hierarchy.

### FR-IMP-005 — No Import Reorganization

Import shall not automatically move or rename physical files.

### FR-IMP-006 — File Fingerprint

The system shall maintain a file fingerprint/hash separately from the Clip's internal ID.

### FR-IMP-007 — Progress

The UI shall provide progress feedback for large imports.

---

# 7. Clip Requirements

### FR-CLIP-001 — Stable Identity

Every Clip shall have an internal stable identifier independent of its file hash.

### FR-CLIP-002 — Physical Path

Every Clip shall maintain its expected physical path.

### FR-CLIP-003 — Original Filename

The system shall preserve the original filename.

### FR-CLIP-004 — Title

Every Clip shall have exactly one logical title.

### FR-CLIP-005 — Single Folder Membership

A Clip shall belong to exactly one current project Folder.

### FR-CLIP-006 — Status

A Clip shall have at least `AVAILABLE` and `MISSING` states.

### FR-CLIP-007 — No Duplicate Virtual Placement

The MVP shall not represent the same Clip simultaneously in multiple virtual folders.

---

# 8. Folder Requirements

### FR-FOLDER-001 — Hierarchy

Folders shall support arbitrary nesting.

### FR-FOLDER-002 — Root Folder

The project root shall act as the top-level virtual folder.

### FR-FOLDER-003 — Create

The user shall be able to create folders.

### FR-FOLDER-004 — Rename

The user shall be able to rename folders.

### FR-FOLDER-005 — Move

The user shall be able to move folders within the hierarchy.

### FR-FOLDER-006 — Delete

The user shall be able to delete folders subject to deletion rules.

### FR-FOLDER-007 — Folder Deletion Prompt

If deleting a folder containing clips, the system shall offer at minimum:

- move clips to parent;
- remove clips from project;
- cancel.

Physical files shall not be deleted by this operation.

---

# 9. Metadata Requirements

### FR-META-001 — Metadata Extraction

The system shall extract available metadata from supported video files.

### FR-META-002 — Raw Metadata Preservation

The system shall preserve raw metadata where practical.

### FR-META-003 — Normalization

The system shall map camera/file-specific metadata keys into standardized application categories.

### FR-META-004 — Camera Independence

The user shall not be required to understand camera-specific metadata key names.

### FR-META-005 — Immutable Metadata

Metadata shall not be directly editable through the organizer.

### FR-META-006 — Standard Categories

The system should support categories including:

- Time
- Location
- Camera
- Lens
- Resolution
- Frame Rate
- Codec
- Author/User
- Duration
- Orientation

Additional categories may be added later.

### FR-META-007 — Missing Values

The system shall represent missing metadata explicitly rather than silently excluding the clip.

### FR-META-008 — Raw Location

The MVP shall display location as raw coordinates and shall not require geocoding.

---

# 10. Tag Requirements

### FR-TAG-001 — Tag Creation

The user shall be able to create tags.

### FR-TAG-002 — Tag Assignment

A Clip may have multiple tags.

### FR-TAG-003 — Tag Removal

The user shall be able to remove tags from Clips.

### FR-TAG-004 — Tag Independence

Tags shall be distinct from immutable camera/file metadata.

---

# 11. Organization Requirements

### FR-ORG-001 — Metadata Selection

The user shall be able to select available normalized metadata categories for organization.

### FR-ORG-002 — Multiple Criteria

The user shall be able to select multiple organization criteria.

### FR-ORG-003 — Criterion Ordering

The user shall be able to specify the ordering of organization criteria.

### FR-ORG-004 — Hierarchical Grouping

The organization engine shall construct nested folders according to the selected criteria.

### FR-ORG-005 — Virtual Proposal

Automatic organization shall initially modify only the virtual project state/proposal.

### FR-ORG-006 — Naming Template

The user shall be able to specify a filename naming template.

### FR-ORG-007 — Collision Handling

The system shall prevent automatic overwriting of existing files.

### FR-ORG-008 — Manual Overrides

Manual organization decisions shall take precedence over automatic organization.

### FR-ORG-009 — Reset to Automatic

The user shall be able to remove a manual override and return a Clip to automatic organization.

### FR-ORG-010 — Restart Organization

The user shall be able to discard the current automatic organization and generate a new proposal.

---

# 12. Naming Requirements

### FR-NAME-001 — Logical Title

The Clip title shall represent its intended new filename.

### FR-NAME-002 — Template

The system shall support a configurable naming template.

### FR-NAME-003 — Numbering

The system shall support sequential numbering.

### FR-NAME-004 — Extension Preservation

The original/appropriate video extension shall be preserved unless an explicitly supported future feature changes it.

### FR-NAME-005 — Invalid Characters

The system shall validate generated names against filesystem naming constraints.

---

# 13. Change Management Requirements

### FR-CHANGE-001 — Explicit Changes

The system shall represent proposed operations explicitly.

At minimum:

- MOVE_CLIP
- MOVE_FOLDER
- RENAME_CLIP
- RENAME_FOLDER
- CREATE_FOLDER
- DELETE_FOLDER

### FR-CHANGE-002 — Change Source

Changes shall distinguish automatic and manual origin where applicable.

### FR-CHANGE-003 — Review

The user shall be able to review proposed changes before Apply.

### FR-CHANGE-004 — Undo

Virtual changes shall support explicit Undo.

### FR-CHANGE-005 — Session Undo

MVP undo history need not persist across application restarts.

---

# 14. Review Requirements

### FR-REVIEW-001 — Change List

The system shall display pending changes.

### FR-REVIEW-002 — Move Visibility

The review interface shall show source and destination.

### FR-REVIEW-003 — Rename Visibility

The review interface shall show old and new names.

### FR-REVIEW-004 — Folder Creation Visibility

The review interface shall show folders that will be created.

### FR-REVIEW-005 — Preflight

The system shall validate changes before applying them.

---

# 15. Filesystem Apply Requirements

### FR-APPLY-001 — Explicit Apply

Physical filesystem changes shall require explicit user confirmation.

### FR-APPLY-002 — Create Directories

Apply shall create required directories.

### FR-APPLY-003 — Move Files

Apply shall move files according to approved changes.

### FR-APPLY-004 — Rename Files

Apply shall rename files according to approved changes.

### FR-APPLY-005 — No Overwrite

Apply shall never silently overwrite an existing file.

### FR-APPLY-006 — Partial Failure

The system shall support partial success and detailed error reporting.

### FR-APPLY-007 — Result Reporting

The system shall report successful and failed operations.

### FR-APPLY-008 — Database Reconciliation

The project database shall be reconciled with actual filesystem results.

### FR-APPLY-009 — Project File Protection

The project file shall remain at the project root.

---

# 16. File Deletion Requirements

### FR-DEL-001 — No Physical Delete

The MVP shall not physically delete video files.

### FR-DEL-002 — Project Removal

A Clip may be removed from the project without deleting its physical file.

---

# 17. Missing File Requirements

### FR-MISS-001 — Detection

The system shall detect when an expected file is missing.

### FR-MISS-002 — Status

The system shall mark the Clip as `MISSING`.

### FR-MISS-003 — No Automatic Relocation

The MVP shall not automatically search for or relocate missing files.

### FR-MISS-004 — No Relink UI

A Locate File/relink feature is outside MVP scope.

---

# 18. UI Requirements

### FR-UI-001 — macOS Appearance

The application shall provide a native-feeling macOS interface.

### FR-UI-002 — Dark Mode

The application shall support a dark-mode-oriented visual design.

### FR-UI-003 — Tree View

The application shall provide an interactive hierarchical tree.

### FR-UI-004 — Canvas View

The application shall provide a visual representation of the same hierarchy.

### FR-UI-005 — Shared Model

Tree and canvas shall operate on the same underlying project model.

### FR-UI-006 — Inspector

The application shall provide a detail/inspector view for selected objects.

### FR-UI-007 — Organization Panel

The application shall provide controls for organization criteria and naming.

### FR-UI-008 — Review Panel

The application shall provide a review interface for pending changes.

### FR-UI-009 — Search

The MVP should support search across basic organizational fields and metadata.

---

# 19. Performance Requirements

### NFR-PERF-001

The UI shall remain responsive during large imports.

### NFR-PERF-002

Metadata extraction shall execute asynchronously where practical.

### NFR-PERF-003

Hashing shall execute asynchronously where practical.

### NFR-PERF-004

The database shall use indexes appropriate for large clip collections.

### NFR-PERF-005

The tree UI should use virtualization/lazy loading where required for large projects.

---

# 20. Reliability Requirements

### NFR-REL-001

The application shall avoid corrupting project state when an individual filesystem operation fails.

### NFR-REL-002

Apply operations shall be individually tracked.

### NFR-REL-003

The application shall be capable of determining which Apply operations succeeded after an interrupted operation.

### NFR-REL-004

The application shall not claim a filesystem operation succeeded unless success has been confirmed.

---

# 21. Data Integrity Requirements

### NFR-DATA-001

Clip IDs shall remain stable across renames and moves.

### NFR-DATA-002

File hashes shall be separate from Clip IDs.

### NFR-DATA-003

Folder parent/child relationships shall remain consistent.

### NFR-DATA-004

A Clip shall have at most one active Folder parent.

### NFR-DATA-005

Project references shall not point to nonexistent database objects.

---

# 22. Security and Privacy

The MVP shall operate locally.

The application should not require uploading footage to a remote service.

Metadata and organizational information should remain local unless a future feature explicitly introduces a remote service.

The application should request only the filesystem permissions necessary for its operation.

---

# 23. Extensibility Requirements

The architecture shall permit future addition of:

- AI video analysis;
- semantic search;
- duplicate detection;
- file relinking;
- geocoding;
- advanced temporal grouping;
- multiple projects;
- cloud synchronization;
- richer media playback.

These features should be layered onto the existing project model rather than requiring fundamental redesign.

# 24. MVP Exclusions

The following are explicitly excluded:

- video editing;
- transcoding;
- sophisticated playback;
- AI analysis;
- object detection;
- face recognition;
- speech recognition;
- semantic search;
- duplicate merging;
- physical file deletion;
- automatic missing-file relocation;
- geocoding;
- multiple simultaneous projects;
- saved organization proposal history;
- persistent undo;
- collaboration;
- cloud synchronization.

# 25. Acceptance Criteria

The MVP shall be considered functionally complete when a user can:

1. Select a footage root.
2. Create/open a project.
3. Scan a large directory of video files.
4. See clips in a project tree.
5. Inspect extracted metadata.
6. Select metadata organization criteria.
7. Generate an automatic virtual hierarchy.
8. Edit that hierarchy manually.
9. Create and apply tags.
10. Rename clips.
11. Use a naming template.
12. Review generated filesystem changes.
13. Undo virtual edits.
14. Preflight changes.
15. Apply changes.
16. Receive a detailed success/failure report.
17. Reopen the project and see the resulting organization.
18. Have missing physical files represented as Missing.
19. Never have an existing file silently overwritten.
20. Never have a video physically deleted by MVP organization operations.

---

# 26. Design Invariants

The following are fundamental system invariants:

1. A Clip has exactly one current Folder.
2. Clip identity is independent of file hash.
3. Metadata is immutable through the organizer.
4. Tags are user-controlled.
5. Automatic organization is a proposal.
6. Manual decisions override automatic organization.
7. Automatic organization does not directly modify the filesystem.
8. Apply is required for physical changes.
9. MVP does not physically delete footage.
10. The `.project` file remains at the project root.
11. The project root is never renamed.
12. Existing files are never silently overwritten.
13. Missing files remain represented in the project.
14. Tree and canvas represent the same underlying hierarchy.
